Azure Kusto query acceleration over Delta: lessons learned

We pointed Kusto query acceleration (QAP) at external Delta tables, ran Delta maintenance on them, and counted which Parquet files Kusto downloaded again. This page is the interactive version of README.md.

TL;DR: does it make Kusto reread files that did not change?

OperationRereads unchanged files?What we saw
OPTIMIZEYes, oftenAll 7 16-file trials reread unchanged files: 3 to 19 of 19 in the window, or (run 4) only in late logs. 2-file trials never did.
PURGEYes, often16-file trials reread all 18 unchanged files in 4 of 6 trials. 2-file trials did once in 6.
VACUUM (isolated)Not observed0 rereads in 4 of 4 isolated scale trials. It writes no commit, so the Delta snapshot does not change.
Reload (control)Yes, on purposeThe scale-run controls reread 6 of 6 files. Proves the storage logs can see rereads.
AppendNo excess pending filesA small append showed 1 pending file for 1 new file (2026-10-30 matrix). Aggregate pending counts alone do not prove zero unchanged-file reads.

These are bounded observations, not guarantees for every table or watch window.

Rule of thumb: any commit that removes files can make Kusto rebuild extents that also hold untouched files. Budget each remove commit as a possible full re-ingest of the table.

How QAP reads an external Delta table

Each operation, before and after

Every table starts with the same small layout: two expired files (A, B), two small files to compact (C, D), one control file (E) and one live file (F), each 32 MiB, in four Hive partitions. A 16-file table has 16 files in each of the expired and compact partitions instead of 2.

OPTIMIZE

Commit removes C and D, adds G. Kusto only needs G, but big tables reread the rest.

PURGE

Commit removes the expired partition. Nothing to read, yet big tables reread everything left.

VACUUM

No commit. Blobs that were already removed get deleted. Kusto reads nothing.

Reload

Drop and recreate the table. Kusto must read every file. This proves the logs work.

Azure setup

Run it

The defaults below were exercised against Azure on 2026-10-31. npx nx run azure-qap-experiment:run -- --help and the experiment README in experiments/azure-qap/ describe the current CLI contract.

Quick demo (about 5 minutes plus a bounded log wait)

The defaults run each operation once, on the small 6-file table with 1 MiB files, four trials at a time.

npx nx run azure-infra:provision
npx nx run azure-qap-experiment:run

Measured on 2026-10-31: about 5m13s to finish the observation windows, then about 4m42s waiting for logs; 9m58s total including cleanup. Provisioning and first-time builds are separate. Azure warm-up and log ingestion latency affect these timings.

Quick-run checkResult
OPTIMIZE / PURGE / isolated VACUUMEach observed 0/4 unchanged files reread in the short window.
Reload controlDetected 6/6 unchanged files reread.
VACUUM isolationDeleted 2 tombstoned files; Delta version stayed at 3.
Report and cleanupAll four telemetry statuses complete, exit 0, cleanup done.
Larger check: 16 files per mutable partition, still 1 MiB10m35s; reload detected 34/34, OPTIMIZE and PURGE observed 0/18; no VACUUM trial.

The larger check retained late-logs-pending for reload at the cap, even though all control files had been observed. A detected control does not make the remaining byte counts final. Tiny files and a short tail demonstrate the tools, not a guaranteed maintenance reread.

Long version (historical 32 MiB fixture size, longer watch)

Use this to investigate the 16-file behavior above; a particular reread outcome is not guaranteed.

npx nx run azure-qap-experiment:run -- --files 16 --file-mib 32 --repetitions 2 --tail 10m --budget 1h

Raise --budget whenever you lengthen --tail: the runner refuses a budget smaller than the tails alone, which is the number of rounds (trials divided by --parallel, rounded up) times --tail. Four operations times two repetitions is eight trials; at four in parallel that is two rounds of 10-minute tails, or 20 minutes, which does not fit the default 15-minute budget. Every regression also restarts a tail. The quick command needs no override.

Flags

FlagDefaultWhat it does
--operations <list>optimize,purge,vacuum,reloadWhich trials to run.
--files <n>2 (2 to 128)Files in each of the expired and compact partitions. 2 makes the 6-file table drawn above; 16 makes 34 files.
--file-mib <n>1 (1 to 32)Size of each Parquet file. The long proof used 32.
--repetitions <n>1 (1 to 10)Trials per operation. Use 2 or more before you conclude anything: small tables are random.

--log-wait <dur>5mLongest wait for late StorageBlobLogs rows. 0 skips it, and is refused when reload is included.
--budget <dur>15mHard cap for all trials, log wait included. Must cover the tails alone: rounds (trials ÷ --parallel, rounded up) × --tail. Cleanup gets up to 5 more minutes.
--env <file>.envEnv file with the sandbox settings.
--out <dir>.temp/experiments/azure-qap/<runId>Where report.md, report.json, evidence.jsonl and queries/ go.
-h, --helpPrint the flags and exit.

Bad flags exit with code 2 before anything is created.

Phases

Seed → accelerate → mutate → tail → log wait → report. Each trial has a name: the operation, plus _2, _3 and so on for later repetitions (purge, purge_2). Its fixtures go to experimentqap/runs/<runId>/<trial>/ and its table is qap_<runId>_<trial>. Run IDs look like 20250102t030405_ab12.

Cleanup always runs, even when a phase fails or you press Ctrl+C. It drops every qap_<runId>_<trial> table and deletes experimentqap/runs/<runId>/, with up to 5 minutes beyond the budget. It prints manual cleanup commands only if it fails. The storage logs are kept separately.

Reading the result

The run writes report.md, report.json, evidence.jsonl and one saved Log Analytics query per trial in queries/ to --out. Each trial ends with one status:

  • complete: the log wait saw the trial's rows settle.
  • late-logs-pending: the log wait ended while rows could still arrive. A 0 here is not yet a 0; rerun the saved query later.
  • budget-exceeded: the budget cut the trial short. Its result is unknown, not 0.
  • failed: the trial hit an error; report.md says which.
CodeMeaning
0Report written without failures. Late logs may remain pending, but every included reload control must already be detected.
1An error, a failed trial, failed cleanup, or an included reload control not seen rereading every unchanged file, for any reason, pending logs and budget included.
2Bad flags or a bad scenario.json.
130Interrupted; cleanup still ran.

The reload control is why a missing reread is a failure, not a pass: if the logs never show the reload's rereads, they could not have shown any other reread either, so the run's zeros prove nothing. Missing telemetry never means “no rereads”.

Clean up

npx nx run azure-infra:reset

reset on its own only previews. With --execute it:

  • deletes the main arrowcol Kusto database; provision recreates it;
  • empties the experimentqap database, dropping every table, external table, function and materialized view, but keeps the database and its managed identity policy;
  • deletes every blob in the arrowcol, checkpoints and experimentqap containers, but keeps the containers.

It keeps the account, cluster, managed identity and Log Analytics workspace, and the logs already in the workspace. Run npx nx run azure-infra:provision after a reset.

Debug it

The Kusto commands need the run's tables, so use them while the run is going: it prints each table name as it creates it, and drops the tables at the end. Run them in the Azure Data Explorer web UI against database experimentqap. Replace qap_<runId>_purge with your table.

Is the policy on?

.show external table qap_<runId>_purge policy query_acceleration
| project Policy = todynamic(Policy)

Is it caught up?

.show external table qap_<runId>_purge operations query_acceleration statistics
| project ExternalTableName, IsEnabled, AccelerationPendingDataFilesCount,
          AccelerationPendingDataFilesSize, AccelerationCompletePercentage,
          LastUpdatedDateTime, NotHealthyReason

Is it healthy?

.show external table qap_<runId>_purge details
| extend State = todynamic(QueryAccelerationState)
| project State.IsHealthy, State.NotHealthyReason, State.CompletionPercentage,
          State.PendingDataFilesCount, State.LastUpdatedDateTime

Which extents hold which partitions?

This reads the table, so run it before or after a watch window, not during one.

external_table("qap_<runId>_purge")
| summarize Rows = count() by Partition = __arrowcol_ingestion, Extent = tostring(extent_id())
| order by Partition asc, Extent asc

Is the cluster out of acceleration capacity?

.show capacity
| where Resource == "QueryAcceleration"

Did my own queries read the lake?

.show queries
| where StartedOn > ago(1h)
| extend External = OverallQueryStats.input_dataset_statistics.external_data
| project StartedOn, Text, External

Which files did Kusto read? (Log Analytics)

The run saves this query for each trial, already filled in, as queries/<trial>.kql (see below). To write it by hand, first get the identity's object ID:

az identity show -g rust-playground -n arrowcol-kusto-reader --query principalId -o tsv
StorageBlobLogs
| where TimeGenerated > ago(3h)
| where AccountName == "arrowcol<sandboxId>"
| where Category == "StorageRead"
| where Uri contains "/experimentqap/runs/<runId>/"
| where RequesterObjectId =~ "<kusto-identity-object-id>"
| where OperationName in ("GetBlob", "ReadFile")
| where toint(StatusCode) between (200 .. 299)
| extend File = tostring(parse_url(Uri).Path)
| summarize Reads = count(), MiB = round(sum(ResponseBodySize) / 1048576.0, 1),
            FirstRead = min(TimeGenerated), LastArrived = max(ingestion_time()) by File
| order by FirstRead asc

How late are the logs?

StorageBlobLogs
| where TimeGenerated > ago(3h)
| where Uri contains "/experimentqap/runs/<runId>/"
| extend LagMinutes = (ingestion_time() - TimeGenerated) / 1m
| summarize p50 = percentile(LagMinutes, 50), p95 = percentile(LagMinutes, 95), Max = max(LagMinutes)

Rerun the log queries after cleanup

The Log Analytics queries keep working after the run has cleaned up, and after azure-infra:reset. The rows live in the workspace, not in the tables or blobs, and stay until the workspace's retention expires.

The run saves two queries per trial in its --out folder, by default .temp/experiments/azure-qap/<runId>/queries/:

  • <trial>.kql groups reads by file and Phase. Rows with Phase set to after-mutation and a GetBlob or ReadFile on a file the mutation did not touch are rereads. late rows arrived after the watch window ended.
  • <trial>.raw.kql lists the individual requests.

Both start from a fixed datetime(), so they need no editing. When logs are still pending, the run prints the exact command; it looks like this, with the workspace's customer ID filled in:

az monitor log-analytics query -w <workspace-customer-id> \
  --analytics-query @.temp/experiments/azure-qap/<runId>/queries/<trial>.kql -o table

To look up the customer ID yourself:

az monitor log-analytics workspace show -g rust-playground \
  -n "arrowcol-<sandboxId>" --query customerId -o tsv

You can also paste a query file into the workspace's Logs blade. For the handwritten queries above, widen TimeGenerated > ago(3h) so it still covers the run. Compare the paths with the run's report.md and evidence.jsonl; after cleanup the fixture blobs, Delta logs included, are gone.
