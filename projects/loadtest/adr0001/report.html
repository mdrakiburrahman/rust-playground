How to read R1, R2, R3 and the run order

R = repetition; each row is a pair of full runs. R1, R2 and R3 repeat the same 56-input, nine-phase workload with the same binaries, two tables, batch sizes, concurrency and resource caps. Each arm starts with fresh isolated SQL/Delta state. These are not three configuration variants. Within each run, the tables and commit history accumulate across phases.

Order = which complete design ran first, not packet or row ordering. R1: Pingora then ADR; R2: ADR then Pingora; R3: Pingora then ADR. Runs are sequential on one host. Host cache state, disk activity, scheduling and background contention can favor either position. Reversing order reduces a fixed first/second-position bias; it does not prove that order caused a result or eliminate it with only three pairs. Cold deployment state does not reset host caches.

Why the shared path is expensive: code evidence, not a timed cost allocation

sql_publication.rs::materialize revisits every accepted decision, verifies data, checks/installs logs and repeats SQL receipt/authority operations before and after each new publication. prepare reconstructs a private Delta log for schema and data preparation, including unchanged-schema probes, and decodes/re-encodes staged Parquet. delta_backends.rs uses fresh unpooled SQL connections and a single locked serialized deployment-state row; collector/publisher per-table serialization adds queueing. These verified implementation costs are shared by both arms, not proof of intrinsic Pingora, Arrow Flight or Delta latency. Existing measurements cannot assign exact milliseconds to each cause.

A future routing-versus-collector experiment needs correlated per-request spans for gateway resolution/forwarding, collector decode/admission/queue/staging, publisher acceptance/materialization and final receipt. 03 / What matters

Four takeaways, without a proxy verdict.

  1. Speed is measured; cause is not. Per-batch staging, fsync, admission and CAS may add cost. No stage breakdown proves the bottleneck.
  2. The safety gain is the commit boundary. ADR validates ownership and publishes reader head atomically; a cached lease alone cannot authorize publication.
  3. More replicas do not split a hot table. Placement can move ownership, not parallelize one table. Scaling phases are distinct workloads.
  4. Resource samples are not efficiency scores. Staggered cgroup sums and sparse CPU intervals are not integrated CPU/byte or continuous peaks; lower memory alone proves no efficiency win.
04 / Balanced design choices

Performance result ≠ safety equivalence.

Baseline / Pingora + SQL + Delta

  • Pros Faster measured end-to-end path; existing Delta publication and buffered flush.
  • Cons SQL/Hive dependencies; sole disk-controller authority; ownership/receipts and Delta publication are separate boundaries. Automatic HA parity was not demonstrated.

Fenced ADR / native + etcd

  • Pros Explicit atomic owner/head fence; exercised stale-owner/recovery proofs; persisted migration reservations and local generation barriers.
  • Cons Slower here; per-batch durable files and control coupling are plausible costs, not isolated causes. No compaction/orphan GC or production HA proof.

Architectures and technologies

Original architecture

Bounded native PyArrow clients → signed edge metadata → Pingora gateway(s) → original disk-backed routing/direct Rust collectors → SQL ownership/receipts + Delta data. SQL Server and Hive dependencies count in resource snapshots.

Additional architecture

Retaining native PyArrow clients → HMAC-authenticated Flight gateway(s) → generation-bound manifest collector adjunct → immutable Parquet/parent manifests. Gateway cache ← snapshot/revision/long-poll bridge ← combined Rust controller → three-member authenticated etcd.

Authoritative boundary

Parquet and manifest finalized first. ONE etcd transaction checks live control + member identities/revisions + exact table record, epoch, lifecycle, pending admission and old head, then changes reader-visible head. Only then TABLE_COMMITTED.

Arrow Flight/tonic stream forwarding uses raw messages and bounded channels, not array decoding in the gateway. Collectors decode only their admitted streams and serialize each table through one local mailbox. Rust ArrowWriter writes immutable Parquet. Readers traverse committed references, never glob staged objects. Arrow schemas/table UUIDs come from the canonical catalog SDK. Equal schemas do not merge table ownership; statically registered versions evolve under one immutable table ID; live catalog/DDL registration is absent.

Placement uses measured cgroup CPU, RSS, active streams and centralized assigned-owner counts. The final revision accounts for persisted target reservations with global/per-target migration budgets, reconstructs them on restart and releases them on completion/failure. Historical cohort b predates these fixes. Migration is persisted DRAINING → higher-epoch RECOVERING → exact-head ACTIVE, with a bounded admission drain. An elephant table still has one owner; there is no autoscaler or ingestion WAL.
