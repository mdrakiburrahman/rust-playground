2. Architecture: separate routing authority from publication authority

Why two authorities?

Routing authority answers which collector process owns a typed table and at what routing epoch. SQL publication authority fences who may publish buffered data and records receipt status. A disk ownership transfer alone must not authorize a second publisher. SQL Server, catalog migrations, Hive metastore and Delta publication are retained, not replaced with a disk-only database.

Router 1 combines ingress, placement and an authenticated private API in one process. Router 2 has its own Pingora ingress but calls router 1 through RemoteRoutingStore; it does not open the disk directory or choose a competing owner. This separates data-router scaling from placement, not controller availability.

3. Ownership, pressure and failure semantics

Sticky table ownership, not per-batch balancing

  • The routing key is (implementation_pool, catalog, schema, table). The schema fingerprint is a separate validated identity, not another table-owner key. This benchmark uses the direct pool.
  • One owner receives all new admitted RPCs for that table. Initial cold placement uses least_pressure or the matched weighted_rendezvous policy. Warm requests retain ownership; adding a collector does not rebalance existing tables automatically.
  • Least-pressure ranks eligible collectors by maximum observed pressure plus pending-reservation pressure: max_pressure_bps + pending × 10000 / max_concurrent_streams, with process-ID tie-breaking. Reservations are centrally bounded (4,096 entries) and expire; they reduce concurrent cold-claim pile-up.
  • Weighted rendezvous orders a hash of table key and process UUID, weighted by stream capacity, remaining pressure headroom and warm-up. Stable instance keys match across runs, but process UUIDs do not; identical owner maps are neither required nor established.
  • Freshness, readiness, pool identity, accepting-deliveries state, subsystem health and hard-pressure eligibility apply before selection. Missing/stale health is not presumed healthy. CPU, RSS, cgroup memory, active streams, buffer bytes/rows/batches, available permits, pending commits and subsystem pressure contribute conservatively through their maximum normalized value, not an average that hides a saturated subsystem.

The harness configures 1-second router refresh/collector heartbeat, a 3-second routing/pressure freshness bound and 30-second routing lease TTL. A cached view is a bounded optimization, not permission to accept stale ownership: collectors perform authoritative new-RPC owner/epoch/admission checks. Existing admitted work has a distinct drain lifecycle. No per-batch redistribution, automatic rebalance or transparent DoPut replay is implemented.

Durability is serialized; uncertainty fails closed

DiskRoutingStore implements the pluggable RoutingStore interface. It holds an exclusive writer lock and serializes compare-and-swap mutations through persistence: bounded version-1 JSON payload, SHA-256 checksum, pending-file write, file sync, atomic rename and parent-directory sync. Acknowledgement follows durable publication. Corruption, unsupported versions and missing previously established state are rejected rather than resetting epochs. Telemetry is not restored after restart; fresh registrations/pressure are required.

During an uncertain commit the authority blocks operations until restart and snapshot inspection. This is deliberate fail-closed behavior, not automatic outage recovery. The retained incident in Section 9 matters to availability claims.

Authentication remains on the real path

Native clients sign the existing edge-HMAC contract (method/path, timestamp, nonce and signed routing metadata). Pingora verifies it and issues the existing internal signed identity for collectors; wire schema/fingerprint validation and ownership checks remain enforced. The private bearer API uses separately provisioned roles: operator for moves/drains, data router for claims, and collector credentials bound to instance keys and current process identities for registration, telemetry and migration acknowledgements. The local transport is private-network cleartext, not a demonstrated Internet TLS deployment. No authentication-bypass claim is made.

Hot-table and availability limits. One hot table is still bounded by its one collector's admission/publication capacity. More routers or collectors do not shard that table. Router 1 remains a fixed single-controller dependency: no election, replicated store, automatic failover or HA.

5. Methodology: reconcile output, not just completed requests

  1. Fresh, separate state for each policy. Prepare a unique task project/network, start three Direct collectors and router 1, then generate canonical schemas/SDK descriptors through the existing native Rust catalog flow. Reusing owned tables would test sticky warm routing, not initial placement.
  2. Cold, three warm repetitions, new-table pressure. Each policy runs the same five phase inputs. The pressure scenario runs a bounded approximately 75%-duty CPU worker inside collector 1's cgroup; it measures real telemetry rather than injecting fictitious store pressure.
  3. Finite real Flight workload. Three native OS workers; 32 rows/batch; two batches/stream; 12 streams per cold/warm phase and 18 streams for pressure. Bounds: 1,048,576 Arrow bytes/batch, 15 seconds/stream generation, 30-second RPC timeout, 30-second scenario generation bound and a shared 60-second publication deadline. Maximum outstanding Arrow byte budget: 3,145,728. Fixed-length random run markers preserve exact generated-byte matching.
  4. Locust does scheduling, native workers do blocking I/O. With LOCUST_SKIP_MONKEY_PATCH=1, a bounded gevent native thread pool performs blocking PyArrow Flight. Users cannot exceed the worker bound. Flight, publication polling and native scanning must not block the gevent hub. The standalone worker uses the same native adapter; connection/stream rotation is finite.
  5. Four distinct outcomes. Generated/attempted/write-completed batches are separate from terminal RPC success, durable admission receipts, and published output. Receipts require published plus purge_allowed. Independently scanned Delta rows must match the exact run/stream/batch/row marker multiset, including duplicate/missing checks. Aggregate Delta commits may cover several receipts; aggregate commit rows are not treated as per-receipt row counts.
  6. Retain ambiguity. Unknown RPC outcomes, pending/failed publication, worker exit failures and unconfirmed output remain visible. No DoPut replay is used to turn a failure into success. This is bounded reconciliation evidence, not an exactly-once guarantee.

The raw settings, streams JSONL, report JSON, Locust files, authority snapshots, placement decisions and controller logs are retained under each evidence directory. All ten matched phase reports were cross-checked against the comparison summary for generation, latency, elapsed duration, generator resources and reconciled throughput.

Metric definitions. Terminal latency measures the native upload operation through terminal completion, not asynchronous publication. Elapsed rows/s divides reconciled rows by the report's elapsed seconds, which include receipt publication and independent output scanning (and Locust scheduling overhead). CPU seconds and peak RSS are load-generator process-lifetime counters. They are not per-request CPU or container memory. No metric here is isolated proxy throughput.

Observed UTC phase coverage (first cold stream → pressure reconciliation): weighted-rendezvous 2026-10-24 00:45:07.002 → 00:47:41.576; least-pressure 2026-10-24 00:56:33.408 → 00:59:04.492. Observed placement decisions under real pressure

In the six new-table decisions, LP assigned zero tables to collector 1 while its measured CPU pressure was 7,621 basis points (76.21%). Collector 2 received four and collector 3 received two. WR assigned one table to collector 1 (77.05% measured CPU at that decision), four to collector 2 and one to collector 3. That is consistent with weighted hashing retaining a nonzero chance for an eligible pressured collector; it is not an authentication or ownership failure. These are six decisions per policy, not a statistically representative distribution.

Interpretation

LP's terminal p50 is lower in cold and all three warm observations; WR's is lower in the pressure phase. Yet WR warm-1 has higher elapsed rows/s despite higher terminal latency, because the elapsed measurement includes scheduling, publication and scanning. Warm-3 throughput is almost equal. The useful result is verified semantics and explicit pressure-dependent initial placement, not a blanket policy-speed ranking.

8. Migration and process scaling

  1. 1 · PreparingOperator requests a move. Controller selects an eligible target; target confirms schema and dependencies.
  2. 2 · DrainingSource barrier blocks new RPCs. Already admitted streams finish and buffered work publishes under the exact source lineage.
  3. 3 · ActivatingAfter confirmed SQL release, target receives a greater routing epoch but remains fenced until its SQL publication lease activates.
  4. 4 · CompleteTarget acknowledgement makes the route Active; new work can publish on the new owner. Ambiguous release never forces transfer.

The drain barrier and local stream entry share one mutex, preventing a new local admission racing a zero-active check. Source completion requires table work and conservative buffer/Quiver backlog to drain. Admitted-work publication and renewal of the separate SQL fence survive routing Draining only for the exact holder/epoch. The source releases SQL before acknowledging release; the target acquires SQL before acknowledging activation. Retry/observation uses the acknowledged migration record, not a second requested move.

9. Validation, retained failures and open limits

Checks already recorded by the implementation run

168 Rust tests passed, 0 failed; 8 opt-in Rust tests ignored. Separately, the latest four-package run recorded 84 passed / 7 ignored. Python default discovery recorded 10 passed with 5 live checks skipped; explicit live-root discovery subsequently passed all 5 real-stack checks: valid publication, bad edge HMAC, unsupported protocol, wrong wire schema, and bounded draining/new-RPC rejection. Locked build, strict Clippy (-D warnings), formatting and whitespace checks passed. The ignored Rust checks did not become passes merely because the Python live checks ran.

Retained incidents are part of the result

Uncertain authority commit: unresolved original cause. An earlier project entered uncertain commit state and failed closed. Disk reopen preserved lineage, but the prolonged outage invalidated SQL handles. That project remained safely unavailable after SQL handles expired; it did not automatically recover. Successful fresh projects do not prove automatic recovery of this incident. The original cause remains unproven.
  • Admitted stream interrupted by the original one-second Pingora grace. That attempt had terminal failure and is not counted as a successful pilot. The corrected harness gives requests 65 seconds of grace before runtime teardown, with a 95-second scoped stop. Fresh admitted-stream drain passed; an overlong stream may still fail honestly.
  • Native worker shutdown was not inferred from report contents. An earlier worker aborted after a successful-looking report. Zero fragment readahead then stalled a scan. The corrected scan disables threaded scanning/batch prefetch, retains at most one current fragment and explicitly releases native objects. Fresh successful workers exited zero; the failed attempts remain retained.
  • Earlier live-check assertions failed. Native early rejection can be a stream reset rather than descriptive Flight text; corrected checks use reason counters and no-admission evidence. An earlier admitted source had no saved receipt ledger, so no full client accounting claim is made for that source.
  • Rust smoke initially probed an unselected Dataflow service. The capability probes were scoped to selected scenarios; the corrected native smoke reconciled 88 rows. No Dataflow deployment was needed or established by that fix.

What remains unestablished

  • No production SLO, maximum throughput, safe concurrency ceiling, long-duration stability or rare-tail distribution. These small synthetic, sequential samples have no confidence intervals or randomized trial order.
  • No additional physical capacity from same-host containers; SQL, Hive, disk, generator and independent scans all contend for resources. No isolated proxy-only speed or comparison with another proxy.
  • No HA/election, automatic rebalance, transparent replay, arbitrary process-restart recovery or exactly-once guarantee.
  • No forced host power loss or forced fsync-error experiment. Focused checks cover write/rename/uncertainty handling and acknowledged restart lineage, not every storage failure mode.
  • No claim that stale health is safe to reuse or that target SQL activation can be skipped after a disk transfer. Single-controller availability and single-owner hot tables remain architectural constraints.
